# DB, ER-Diagram, API 명세서 학습 정리

## 1. DB란 무엇인가?

DB(Database, 데이터베이스)는 데이터를 일정한 구조로 저장하고 관리하는 공간이다.

할 일 앱에서는 할 일의 내용, 완료 여부, 카테고리 등을 저장한다. 저장한 데이터는 필요에 따라 조회, 수정, 삭제할 수 있다.

관계형 데이터베이스는 데이터를 테이블 형태로 관리한다.

| 용어 | 의미 | 예시 |
| --- | --- | --- |
| 테이블(Table) | 관련 데이터를 모아 놓은 표 | 할 일 테이블 |
| 행(Row) | 하나의 데이터 항목 | 특정 할 일 하나 |
| 열(Column) | 데이터가 가지는 속성 | 내용, 완료 여부 |
| 기본키(PK) | 각 행을 고유하게 식별하는 값 | 할 일 ID |
| 외래키(FK) | 다른 테이블의 키를 참조하는 값 | 카테고리 ID |

## 2. ER-Diagram이란?

ER-Diagram(ERD)은 데이터의 구성과 관계를 시각적으로 표현한 그림이다. 데이터베이스를 설계할 때 사용한다.

주요 구성 요소는 다음과 같다.

- **엔터티(Entity)**: 관리하려는 대상. 예: 할 일, 카테고리
- **속성(Attribute)**: 대상이 가지는 정보. 예: 내용, 완료 여부
- **관계(Relationship)**: 대상 사이의 연결. 예: 할 일이 카테고리에 속함

관계에는 대표적으로 세 가지가 있다.

| 관계 | 의미 | 예시 |
| --- | --- | --- |
| 1:1 | 하나의 항목이 다른 항목 하나와 연결됨 | 사용자와 사용자 상세 프로필 |
| 1:N | 하나의 항목이 여러 항목과 연결됨 | 카테고리와 할 일 |
| N:M | 양쪽의 여러 항목이 서로 연결됨 | 학생과 수강 과목 |

관계형 DB에서 N:M 관계는 일반적으로 중간 테이블을 만들어 표현한다.

## 3. ER-Diagram 그리는 법

### ① 요구사항에서 엔터티 찾기

할 일 앱에서는 `TODO`와 `CATEGORY`를 엔터티로 정할 수 있다.

### ② 각 엔터티의 속성 정하기

- TODO: ID, 제목, 내용, 완료 여부, 카테고리 ID
- CATEGORY: ID, 이름

### ③ 기본키와 외래키 정하기

각 항목을 구별하기 위해 `id`를 기본키로 설정한다.

TODO의 `category_id`는 CATEGORY의 `id`를 참조하는 외래키로 설정한다.

### ④ 관계와 필수 여부 정하기

- 카테고리 하나에는 할 일이 여러 개 속할 수 있다.
- 할 일 하나에는 최대 하나의 카테고리를 설정한다.
- 미분류를 허용한다면 할 일의 카테고리 ID는 NULL일 수 있다.

따라서 CATEGORY와 TODO는 1:N 관계이다.


## 4. API란 무엇인가?

API(Application Programming Interface)는 프로그램 사이에서 기능이나 데이터를 주고받기 위한 인터페이스이다.

웹 서비스에서는 프론트엔드가 서버에 요청을 보내고, 서버가 응답을 반환하는 방식으로 많이 사용한다.

예를 들어 할 일 등록 버튼을 누르면 다음 과정이 진행된다.

1. 프론트엔드가 사용자가 입력한 내용을 서버에 전송한다.
2. 서버가 내용을 검증하고 DB에 저장한다.
3. 서버가 등록 결과를 프론트엔드에 반환한다.

HTTP를 사용하는 웹 API에서는 메서드로 요청의 목적을 표현한다.

| HTTP 메서드 | 일반적인 용도 |
| --- | --- |
| GET | 데이터 조회 |
| POST | 데이터 생성 |
| PUT | 대상 데이터 전체 교체 |
| PATCH | 데이터 일부 수정 |
| DELETE | 데이터 삭제 |

## 5. API 명세서란?

API 명세서는 API를 어떻게 호출하고 어떤 결과를 받는지 정리한 문서이다.

프론트엔드와 백엔드 개발자가 같은 규칙에 맞춰 개발할 수 있도록 작성한다.

## 6. API 명세서 작성 방법

### ① 필요한 기능 정리하기

할 일 앱을 예로 들면 다음 기능이 필요하다.

- 할 일 등록, 조회, 수정, 삭제
- 할 일 카테고리 설정
- 할 일 완료·미완료 상태 변경
- 카테고리 등록, 조회, 수정, 삭제

완료 여부는 할 일 조회 응답에 포함하여 확인할 수 있다.

### ② HTTP 메서드와 경로 정하기

경로에는 관리 대상의 이름을 사용하고, 특정 항목은 ID로 구분한다.

| 구분 | 기능 | HTTP 메서드 | API 경로 |
| --- | --- | --- | --- |
| TODO | 할 일 등록 | POST | `/api/todos` |
| TODO | 할 일 목록 조회 | GET | `/api/todos` |
| TODO | 할 일 상세 조회 | GET | `/api/todos/{id}` |
| TODO | 할 일 내용 수정 | PATCH | `/api/todos/{id}` |
| TODO | 할 일 카테고리 설정 | PATCH | `/api/todos/{id}` |
| TODO | 할 일 완료 여부 변경 | PATCH | `/api/todos/{id}` |
| TODO | 할 일 삭제 | DELETE | `/api/todos/{id}` |
| CATEGORY | 카테고리 등록 | POST | `/api/categories` |
| CATEGORY | 카테고리 목록 조회 | GET | `/api/categories` |
| CATEGORY | 카테고리 내용 수정 | PATCH | `/api/categories/{id}` |
| CATEGORY | 카테고리 삭제 | DELETE | `/api/categories/{id}` |

`{id}`는 해당 경로에서 다루는 항목의 ID를 의미한다.

- `/api/todos/3`: ID가 3인 할 일
- `/api/categories/2`: ID가 2인 카테고리

할 일 내용, 카테고리, 완료 여부 변경은 같은 수정 API에서 요청 본문을 다르게 보내 처리할 수 있다.

### ③ 요청 데이터 정의하기

데이터를 어디에 전달하는지 구분한다.

| 구분 | 용도 | 예시 |
| --- | --- | --- |
| Path Parameter | 특정 항목 식별 | `/api/todos/3`의 `3` |
| Query Parameter | 조회 조건 전달 | `/api/todos?categoryId=2` |
| Request Body | 등록하거나 수정할 데이터 전달 | 할 일 내용 |

각 필드의 이름, 자료형, 필수 여부, 허용 조건도 작성한다.

예를 들어 카테고리별 할 일 조회는 목록 조회에 Query Parameter를 추가하여 처리할 수 있다.

```http
GET /api/todos?categoryId=2
```

### ④ 응답 데이터와 상태 코드 정의하기

성공했을 때 반환할 데이터와 실패했을 때의 오류 형식을 정한다.

| 상태 코드 | 의미 |
| --- | --- |
| 200 OK | 요청 성공 |
| 201 Created | 생성 성공 |
| 204 No Content | 요청 성공, 응답 본문 없음 |
| 400 Bad Request | 잘못된 요청 |
| 404 Not Found | 대상이 존재하지 않음 |
| 500 Internal Server Error | 서버 내부 오류 |
