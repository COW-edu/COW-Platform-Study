# 2026-2 1주차 백엔드 기초 정리

## 1. 백엔드란?

옛날의 웹->미리 만들어진 HTML 파일을 사용자에게 보여주는 일방향적 방식
하지만 게시판, 검색, 로그인은 사용자의 요청에 따라 그때그때 다른 결과를 도출해야하고 그 요청을 예측할 수 없음

백엔드의 역할-사용자의 요청을 받아 필요한 데이터를 처리하고 결과를 다시 사용자에게 전달

웹 서비스의 종류
프론트엔드-사용자가 직접 보는 화면작업
백엔드(Backend)-사용자의 요청을 처리하고 데이터를 관리

---

## 2. 데이터베이스와 SQL

서비스에서 사용하는 데이터를 계속 보관하기 위해 데이터베이스(DB)를 사용한다.

대표적으로 관계형 데이터베이스(RDB)가 있으며, 데이터를 표와 비슷한 형태로 관리한다.

Row: 하나의 데이터
Column: 데이터의 속성
Schema: 데이터가 어떤 구조로 저장되는지 정의한 것
SQL: 데이터베이스에 데이터를 조회하거나 저장하기 위해 사용하는 언어
Query: 데이터베이스에 보내는 요

대표적인 관계형 데이터베이스의 예시: MySQL 

---

## 3. MVC

프로그램의 규모가 작을 때는 화면을 보여주는 코드, 데이터를 가져오는 코드, 계산을 하는 코드 등을 하나의 파일에 작성할 수도 있지만 프로그램이 커지면서 코드가 복잡해졌을떄 이를 수정하기 어려워질것이다. 이를 해결하기 위해 코드의 역할을 분리하는 방법 중 하나가 **MVC 패턴**이다.

### Model

데이터와 관련된 부분을 담당

### View

사용자에게 보여지는 화면을 담당

### Controller

중간 위치에서 사용자의 요청을 받고 어떤 데이터를 가져올지, 어떤 화면을 보여줄지 등을 결정

또한 서비스에서 실제로 수행해야 하는 핵심적인 규칙이나 처리를 Business Logic이라고 한다.

---

## 4. REST API와 JSON

웹뿐만 아니라 스마트폰 앱 등 다양한 프로그램에서 서버의 데이터를 사용하게 되면서, 서버가 완성된 HTML 화면 대신 필요한 데이터를 전달하는 방식이 중요해졌다.

프론트엔드와 백엔드는 **API**를 통해 서로 데이터를 주고받을 수 있다.

이때 주로 사용하는 데이터 형식 중 하나가 **JSON**이다.

API: 서로 다른 프로그램이 기능이나 데이터를 주고받을 수 있도록 만든 인터페이스
Endpoint: API에 요청을 보내는 주소
JSON: 데이터를 주고받기 위해 사용하는 형식

데이터를 처리하는 기본적인 작업은 CRUD로 구분할 수 있다.
CRUD=
Create
Read
Update
Delete

## 5. HTTP와 로그인

HTTP는 기본적으로 이전에 이루어진 요청을 기억하지 않는데, 이러한 특징을 Stateless라고 한다.

하지만 웹사이트에서는 사용자가 한 번 로그인하면 다른 페이지에서도 로그인 상태가 유지되어야 하기 때문에 이를 위해 Cookie나 Session과 같은 방법을 사용한다고 한다.

Cookie: 브라우저에 정보를 저장하는 방식
Session: 서버에서 사용자의 상태 정보를 관리하는 방식

로그인-인증과 인가의 차이란 무엇인가?

Authentication(인증): 사용자가 누구인지 확인하는 것
Authorization(인가): 해당 사용자가 특정 기능을 사용할 권한이 있는지 확인하는 것

## 6. JWT

로그인 및 인증에 사용되는 방법 중 하나로 **JWT(JSON Web Token)**가 있다.

JWT의 구성요소

 Header
 Payload
*Signature

JWT의 Header와 Payload는 Base64 방식으로 인코딩되어 있지만 암호화되어 있는 것은 아니기 때문에 중요한 정보를 그대로 저장하면 위험하고, 비밀번호또한 해시함수같은 저장방식을 이용하는게 좋음

서버에 동시에 들어온 여러 요청을 처리할떄-효율성 향상을 위해 멀티스레드,이벤트 루프등의 방식을 이용

## 8. Cache, Redis, CDN

같은 데이터를 계속 데이터베이스에서 조회하면 서버와 데이터베이스에 부담이 생길 수 있다.

자주 사용하는 데이터를 빠르게 접근할 수 있는 곳에 임시로 저장해두는 것을 **Cache**라고 한다.

**Redis**는 메모리를 이용해 데이터를 빠르게 처리할 수 있어 캐시 등에 사용된다.

**CDN(Content Delivery Network)**은 이미지나 파일 등의 데이터를 여러 지역에 저장해두고 사용자와 가까운 위치에서 데이터를 전달하는 방식이다.

이를 통해 사용자가 데이터를 더 빠르게 받을 수 있다.

---

## 9. Transaction

여러 데이터 처리 작업이 하나의 작업처럼 함께 성공하거나 실패해야 하는 경우 **Transaction**을 사용한다.

성공적인 트랜젝션을 위한 수단
* **Commit**: 모든 작업이 정상적으로 처리되어 결과를 확정하는 것
* **Rollback**: 문제가 발생했을 때 작업 이전 상태로 되돌리는 것

트랜잭션의 중요한 특징은 **ACID**로 표현한다.

* **Atomicity**: 원자성
* **Consistency**: 일관성
* **Isolation**: 격리성
* **Durability**: 지속성

## 10. Scale Up과 Scale Out

기존 서버의 성능만으로 모든 요청을 처리하기 어려울 떄
서버의 처리 능력을 증가시키는 방법 2가지
* **Scale Up**: 기존 서버 자체의 성능을 높이는 방법
* **Scale Out**: 서버의 개수를 늘리는 방법

Scale out의 보완재- **Load Balancer**

## 11. API Gateway와 Message Queue

Microservice처럼 여러 서버를 사용하는 환경에서는 각각의 서비스에 접근할 수 있는 하나의 진입점이 필요할 수 있다.

**API Gateway**는 외부의 요청을 받은 뒤 적절한 내부 서비스로 전달하는 역할을 한다.

예를 들면 다음과 같은 방식으로 요청을 구분할 수 있다.

```text
example.com/mail  → mail.example.com
example.com/user  → user.example.com
example.com/board → board.example.com
```

또한 서비스끼리 작업을 바로 요청하는 대신 **Message Queue**를 이용할 수도 있다.

한 서비스가 처리해야 할 작업을 Queue에 넣어두면 다른 서비스가 해당 작업을 가져가서 처리할 수 있다. 이를 통해 서버에 일시적인 문제가 발생하더라도 작업을 나중에 다시 처리할 수 있다.

---

## 12. CI/CD

프로그램을 개발한 뒤에는 실제 사용자가 이용할 수 있도록 서버에 배포해야 한다.

과거에는 개발자가 직접 서버에 접속해서 파일을 업로드하고 서버를 재시작하는 등의 작업을 해야 했다.

**CI/CD**는 코드의 테스트와 배포 과정을 자동화하여 이러한 작업을 효율적으로 수행할 수 있도록 해준다.

코드가 변경되면 자동으로 테스트를 실행하고, 테스트를 통과한 코드를 서버에 배포하는 등의 작업을 구성할 수 있다.

---

## 13. Docker

개발자의 컴퓨터와 실제 서버의 실행 환경이 다르면 개발할 때는 정상적으로 실행되던 프로그램이 서버에서는 실행되지 않는 문제가 발생할 수 있다.

**Docker**는 프로그램의 코드와 실행에 필요한 환경을 함께 패키징하여 이러한 환경 차이로 인한 문제를 줄이는 데 사용된다.

또한 실제 서비스를 운영할 때는 개발 환경과 운영 환경을 분리하는 것이 중요하다. 개발 과정에서 테스트하는 데이터와 실제 사용자의 데이터가 섞이지 않도록 해야 하며, 운영 환경에서는 로그와 모니터링 등을 통해 서버의 상태를 확인할 필요가 있다.
